# `copy_plane` の一括コピー経路でバックエンド異常時のプレーン実サイズとの整合を追加検証する

Created: 2026-04-01  
Model: Composer 2 Fast

## なぜこの対応が必要か

一括コピー分岐では `copy_size = src_width * src_height`（`checked_mul` 済み）で `copy_nonoverlapping` する。**行ループ分岐**は行ごとに `src_width` バイトを **`dst_stride` 間隔**で書く。両者は **同じ論理サイズ**を前提にしているが、**CV が割り当てるプレーンのバイト数**が **`height * bytes_per_row` より小さい**（理論上のバックエンド異常）場合、**どちらの経路も**外側へ書く余地を完全には論じていない。優先度は低いが、**「対称性で穴」**というより **前提の明示**が必要。

## 現状

- **場所**: `src/lib.rs` の `Encoder::copy_plane`（一括分岐と行ループ分岐）

## 問題（リスク）

- CoreVideo の通常契約では顕在化しにくい。**前任レビューで甘かった点**: 「行ループより弱い」としたが、厳密には **行ループも最終行のあふれ**を別定義にしているなら **同種の前提**に立つ。比較は **式と CoreVideo の保証**に落とす必要がある。

## 望ましい対応の方向（案）

- `CVPixelBufferGetWidthOfPlane` / `GetHeightOfPlane` / `GetBytesPerRowOfPlane` から **当プレーンの格納に必要な最小バイト数の見積り**をし、`copy_size` または行ループ累積と **矛盾しない**ことを検証するか、**Apple ドキュメント上不要**と断言できる根拠をコメントに書く。

## 解決の完了条件（厳格）

- **照合を実装する**か、**「検証不要」であることの根拠（ドキュメント引用）**をコードに残すかの **どちらか**。「対称性がないかも」だけでは **未完了**。

## 厳格レビュー（第 2 パス）

1. **ソース照合**: 一括と行ループの両方を読み、**同じ `copy_size` 論理**であることを確認。
2. **不足していた観点**: 行ループ経路を **自動的に安全側**とみなしていた可能性。
3. **0016 との関係**: 乗算オーバーフローは別途対済。**本件は「割当サイズ」**。
4. **誤解しやすい点**: 偽陽性で **正常環境を拒否**しないよう、式は保守的に。
5. **前回からの差分**: 完了条件を **実装か引用の二択**に固定。

## 解決方法

Completed: 2026-04-01

- `copy_plane` で `CVPixelBufferGetWidthOfPlane` / `GetHeightOfPlane` / `GetBytesPerRowOfPlane` からプレーン格納バイト数を見積り、コピー範囲がそれを超えないことを検証する（コメントで Core Video のプレーン契約を併記）。
