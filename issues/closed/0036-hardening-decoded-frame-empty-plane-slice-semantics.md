# デコード成功時にプレーンが空スライスになる可能性と API の意味を再検討する

Created: 2026-04-01  
Completed: 2026-04-01  
Model: Composer 2 Fast

## なぜこの対応が必要か

`I420Frame` / `Nv12Frame` の `plane_slice` は、NULL または乗算オーバーフロー時に **空の `&[u8]`** を返す。`Decoder::decode` が `Some(frame)` を返した場合でも、呼び出し側は **「有効なピクセルがある」**と読み違えうる。ドキュメント上は注意書きがあるが、**型レベルで失敗にできないか**（例: `Result`・別バリアント）は設計の論点である。

## 現状

- **場所**: `src/lib.rs` の `I420Frame` / `Nv12Frame` と `plane_slice`
- **過去**: `issues/closed/0017-bug-decoded-plane-slice-safety.md` で安全性に関する修正あり。本 issue は **API 意味・完了判定**の整理（再発防止と設計の両方）。

## 望ましい対応の方向（案）

- **現状維持**なら、rustdoc を **より目立つ位置**にまとめる、またはサンプルで **空スライス時の扱い**を示す。
- **変更**するなら、`decode` が異常を `Err` にできるか、プレーン取得を `Option` / `Result` にするか、別型で表すかを検討する（**破壊的変更になり得る**）。

## 解決の完了条件

- 「静かに空」か「明示的に失敗」かの **方針が決まり**、公開 API の説明と実装が一致していること。
- **`Option` / `Result` 等のシグネチャ変更や公開型の変更**を選んだ場合は、`CHANGES.md` の **`[CHANGE]`** に追記し、**破壊的変更**として利用者が追えること。
- **0017** で既に直した部分と **矛盾する説明や二重の論点**が残っていないこと（必要なら 0017 の文脈を参照し、本 issue の完了報告で整理済みと分かること）。

## 解決方法

- `DecodedFrame`、`I420Frame`、`Nv12Frame` の rustdoc を補い、空スライスは異常時のセンチネル**であり** `Result` では表さないことを明示した（**型は変更しない**）。破壊的変更のため `CHANGES.md` の `[CHANGE]` は不要。
