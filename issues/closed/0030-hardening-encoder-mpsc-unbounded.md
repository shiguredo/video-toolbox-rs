# エンコード出力が `mpsc::channel` の無制限バッファでメモリを伸ばし続けうる

Created: 2026-04-01
Model: Composer 2 Fast

## なぜこの対応が必要か

コールバックが **受信側より速く** フレームを送ると、チャンネル内にエンコード済みフレームが蓄積し、**メモリ枯渇・OOM** につながりうる。パニックではないが **実害** がある。

## 現状

- **場所**: `src/lib.rs` の `Encoder` 生成時の `mpsc::channel`（コールバックから `tx.send`）

## 問題（リスク）

- **無制限チャネル**は `send` が **ブロックしない**（メモリが許す限り積む）。`next_frame` を呼ばない利用者は **ヒープを食い続ける**。
- **前任レビューで甘かった点**: 「有界化は設計判断」と逃げたが、**最低限のドキュメント義務**（例: 「一定以上溜めないこと」「`next_frame` を定期的に呼ぶ」）は **設計変更なしで必須**であり、未記載なら **未完了**。

## 望ましい対応の方向（案）

- 有界チャネル + `try_send` + ポリシー（破棄・ログ）を **API 変更として**検討。
- または **公開ドキュメント**に、**バックログが無制限に伸びうる**ことと **受信の推奨頻度**を明記（コード変更なしの線）。

## 解決の完了条件（厳格）

- **ドキュメント追記**または **有界化**のいずれか。どちらもない PR は **未完了**。
- 「将来検討」だけの本文は **却下**。

## 厳格レビュー（第 2 パス）

1. **ソース照合**: `mpsc::channel()` と `send` を確認。無制限である。
2. **不足していた観点**: **ドキュメントのみで足りる最低ライン**を別途定義。
3. **0027 との関係**: `try_recv` で `output_frames` に入るため、**二段のバッファ**（チャネル + HashMap）。
4. **誤解しやすい点**: `send` は **エラーになるのは受信側ドロップ時のみ**（無制限では詰まらない）。
5. **前回からの差分**: 完了条件で **ドキュメントも合格ライン**にした。

## 解決方法

Completed: 2026-04-01

- `Encoder` 構造体の公開ドキュメントに、無制限 `mpsc` と `next_frame` の呼び出し頻度とメモリ滞留の関係を追記した。
