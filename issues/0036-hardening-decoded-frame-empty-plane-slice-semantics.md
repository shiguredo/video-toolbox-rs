# デコード成功時にプレーンが空スライスになる可能性と API の意味を再検討する

Created: 2026-04-01  
Model: Composer 2 Fast

## なぜこの対応が必要か

`I420Frame` / `Nv12Frame` の `plane_slice` は、NULL または乗算オーバーフロー時に **空の `&[u8]`** を返す。`Decoder::decode` が `Some(frame)` を返した場合でも、呼び出し側は **「有効なピクセルがある」**と読み違えうる。ドキュメント上は注意書きがあるが、**型レベルで失敗にできないか**（例: `Result`・別バリアント）は設計の論点である。

## 現状

- **場所**: `src/lib.rs` の `I420Frame` / `Nv12Frame` と `plane_slice`

## 望ましい対応の方向（案）

- **現状維持**なら、rustdoc を **より目立つ位置**にまとめる、またはサンプルで **空スライス時の扱い**を示す。
- **変更**するなら、`decode` が異常を `Err` にできるか、別型で表すかを検討する（破壊的変更になり得る）。

## 解決の完了条件

- 「静かに空」か「明示的に失敗」かの **方針が決まり**、公開 API の説明と実装が一致していること。

## レビュー（第 1 回）— ソース照合

- `plane_slice` は `row_count.checked_mul(bytes_per_row)` が `None` または `0` なら空、`ptr` が NULL なら空。正常系では **非空スライス**が返る想定。
- `decode` は `CVPixelBufferLockBaseAddress` 成功後に `I420Frame` / `Nv12Frame` を構築している。ロックとプレーン参照の前提は **通常は整合**。

## レビュー（第 2 回）— 呼び出し側のバグになりうる経路

- 空スライスは **「そのプレーンが無い」**のではなく **「異常を表すセンチネル」**に近い。利用者が `y_plane().len()` で進めると **ゼロ除算や無処理**になりうる。

## レビュー（第 3 回）— API 破壊の度合い

- `decode` を `Result` に変える・プレーン取得を `Result` にするは **破壊的変更**。マイナーバージョンでは **ドキュメント強化のみ**が現実的な選択肢になりやすい。

## レビュー（第 4 回）— `Option` 化

- `Option<&[u8]>` にすると呼び出しは煩雑になるが **誤解は減る**。トレードオフを issue 本文に追記してもよい。

## レビュー（第 5 回）— テスト

- NULL を強制するのは **統合テストでも難しい**。オーバーフロー経路も同様。**ドキュメント＋サンプル**で完了とするなら、完了条件を緩めて明記する。

## レビュー（第 6 回）— 0017 との関係

- closed の `0017-bug-decoded-plane-slice-safety` と内容が近い。**再発防止**として本 issue は「方針決定」寄り。過去の解決内容と矛盾しないか確認。

## レビュー（第 7 回）— NV12 と I420 の一貫性

- 両方の `plane_slice` が同じセマンティクスか **揃える**。片方だけ `Result` にするのは避ける。

## レビュー（第 8 回）— ログ

- 空スライス時に `log::warn!` を出す案は **ノイズ**になりうる。出すなら **一度だけ**または **debug 限定**を検討。

## レビュー（第 9 回）— パフォーマンス

- `Result` や `Option` 追加は **ホットパスでの分岐増**。実測は任意。

## レビュー（第 10 回）— 締めチェックリスト
