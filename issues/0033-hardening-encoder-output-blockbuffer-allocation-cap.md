# エンコード出力で `CMBlockBufferGetDataLength` に基づく `Vec` 確保に上限がない

Created: 2026-04-01  
Model: Composer 2 Fast

## なぜこの対応が必要か

`process_encoded_output` は `CMBlockBufferGetDataLength` の値で `vec![0u8; block_len]` を確保する。**異常に大きい長さ**（破損データ・実装バグ・悪意ある入力に近い経路）では **OOM** や **サービス拒否相当**になり得る。他の箇所ではパラメータセット長に **ISO 14496-15 に沿った上限**を設けている一方、ここには **防御的上限がない**。

## 現状

- **場所**: `src/lib.rs` の `Encoder::process_encoded_output`（`CMBlockBufferCopyDataBytes` 前の `Vec` 確保）

## 望ましい対応の方向（案）

- 妥当な **最大フレームサイズ**（解像度・ビットレート・コーデックから導くか、定数上限）を検討し、超過時は **エラー扱い・ログ・フレーム破棄**のいずれかで明確に失敗させる（無暗にクランプしないこと。ビットストリームを壊す可能性）。

## 解決の完了条件

- 上限方針が決まり、**コードと短いコメント**で根拠が追試できること。

## レビュー（第 1 回）— ソース照合

- 割当は `process_encoded_output` 内の `CMBlockBufferGetDataLength` → `vec![0u8; block_len]` → `CMBlockBufferCopyDataBytes`。圧縮データは **エンコーダが生成した `CMSampleBuffer` 経由**であり、外部ユーザー入力を直接反映するわけではない。脅威モデルは **「VT が返す異常値」**に近い。
- それでも **OOM でプロセス全体が落ちる**点は防御の価値がある。

## レビュー（第 2 回）— 上限の根拠設計

- 解像度・ビットレートから導く場合、`EncoderConfig` とセッション状態をコールバック側で参照できるかが論点。参照できないなら **定数上限（例: 数十 MB）**＋ログが現実的。
- **クランプしてコピー**は issue 本文どおり避ける。拒否・破棄が安全。

## レビュー（第 3 回）— 既存の `MAX_PARAMETER_SET_COPY_BYTES` との関係

- パラメータセットは ISO 根拠あり。圧縮ビットストリームは別物。**同じ定数を流用しない**方が誤解が減る。別定数・別コメントがよい。

## レビュー（第 4 回）— エラー伝播

- 現状はコールバック内で `log::error!` と `return`。上限超過時も **同様にログして黙って捨てる**のか、**呼び出し側に伝える**のかは API 上難しい。方針を一文で issue 完了報告に書くとよい。

## レビュー（第 5 回）— `block_len == 0`

- ゼロ長のとき `vec![0;0]` は OOM にならない。異常検知として **別扱い**するかは実装次第。

## レビュー（第 6 回）— テスト

- 巨大 `block_len` をモックせずに単体テストするのは難しい。**統合テストで異常系を再現**するか、または **上限定数の境界**だけユニットテストするかの二段構えが現実的。

## レビュー（第 7 回）— パフォーマンスとの兼ね合い

- 上限を小さくしすぎると **正当な高ビットレート 4K** 等で誤拒否のリスク。上限値は **保守的に大きめ**＋ログが無難。

## レビュー（第 8 回）— CHANGES / リリースノート

- 挙動変更（フレームを捨てる）になるなら **後方互換**の見え方に注意。パッチで「異常時に落ちなくなった」と書けるか検討。

## レビュー（第 9 回）— 重複 issue

- 0021（`CMBlockBufferGetDataPointer`）は **読み取り経路**の修正。本件は **確保サイズ**。別 issue のままで正しい。
