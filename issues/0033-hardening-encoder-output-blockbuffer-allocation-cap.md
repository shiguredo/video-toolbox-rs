# エンコード出力で `CMBlockBufferGetDataLength` に基づく `Vec` 確保に上限がない

Created: 2026-04-01  
Model: Composer 2 Fast

## なぜこの対応が必要か

`process_encoded_output` は `CMBlockBufferGetDataLength` の値で `vec![0u8; block_len]` を確保する。**異常に大きい長さ**では **OOM** や **プロセス全体へのサービス拒否相当**になり得る。他の箇所ではパラメータセット長に **ISO 14496-15 に沿った上限**を設けている一方、ここには **防御的上限がない**。

## 脅威モデル（何を防ぐ issue か）

- 圧縮データは **呼び出し元が任意のバイト列を直接 `CMBlockBufferGetDataLength` に渡しているわけではない**。経路は **Video Toolbox のエンコード出力コールバック**内で、**エンコーダが生成した `CMSampleBuffer` → `CMBlockBuffer`** である。
- よって主に想定する異常は **外部からの「悪意あるネットワーク入力」をそのまま読む**というより、**Video Toolbox／CoreMedia の返す長さが異常**（実装バグ・内部状態の破損・極端な設定結果など）である。「悪意に近い」表現だけでは曖昧なので、**コールバック経由・VT 生成データ**であることを前提に書く。

## 超過時の扱い（実装で決める契約）

コールバック内のため **`Error` を呼び出し元にそのまま伝播**しにくい。次のいずれか（または組み合わせ）を **実装時に明示**し、issue 完了時に本文または PR で追試できるようにする。

- **ログ**（例: `log::error!`）して当該フレームを **破棄**する。
- **黙って破棄**にする場合は、**意図的である理由**（ノイズ・スパム防止など）をコメントで補う。
- 呼び出し側へ届けられる設計に変える場合は **別途 API 設計**が必要（スコープ外なら「現状はログ＋破棄」でよいことを明記）。

**クランプして短くコピー**は、ビットストリームを壊す可能性があるため **採用しない**（issue 本文の方針どおり）。

## 現状

- **場所**: `src/lib.rs` の `Encoder::process_encoded_output`（`CMBlockBufferCopyDataBytes` 前の `Vec` 確保）

## 望ましい対応の方向（案）

- 妥当な **最大長**（解像度・ビットレート・コーデックから導くか、**パラメータセット用 `MAX_*` とは別の**定数上限＋根拠コメント）を設け、超過時は上記 **契約に従って失敗**させる。

## 解決の完了条件

- 上限の **数値と根拠**がコードと短いコメントで追試できること。
- **脅威モデル**（VT コールバック経由）と **超過時の契約**（ログ・破棄等）が、実装と一致していること。
